# tv-source

TVBox 内置源清单（远程）。改这里 → 推到 GitHub → 手机上点一次「刷新内置源」，App 里的内置清单就整体换掉。

- 远程仓库（主）：<https://github.com/sukai616/tv-source>（**App 实际拉取源是 GitHub raw**）
- **只有 GitHub**；Gitee raw 曾返回 **451**，现已弃用，不再推送或作为备份。
- 清单地址（App 里已内置，也可手动填）：<https://gh-proxy.com/https://raw.githubusercontent.com/sukai616/tv-source/master/builtin.json>
  - 直连备用：<https://raw.githubusercontent.com/sukai616/tv-source/master/builtin.json>
  - 前缀备用：<https://ghfast.top/https://raw.githubusercontent.com/sukai616/tv-source/master/builtin.json>
  （三条 2026-09-29 实测均 200，内容一致；直连在国内不稳，所以 App 内置默认带 gh-proxy 前缀）

## 怎么用

1. App 里：**设置 → 内置源 → 清单地址**。装好就默认是本仓库这条地址（后面标着「内置」），不用手填；想换别的清单才改。
2. **刷新内置源**：拉取本仓库的 `builtin.json`，覆盖 App 内置的点播 / 直播清单（会提示「刷新完成：点播 x 条、直播 y 条」）。
3. 之后**内置点播源 / 内置直播源**两行里列出的，就是这份清单里的条目；带 `recommended` 的排在最上面，
   名字前有「推荐 · 」，备注写在名字后的括号里。选中即切换当前配置地址。

**直播跟随点播**：设置里有一行开关（默认开启）。开启时换点播会顺带换直播地址，因为单仓 JSON 一般
sites 与 lives 在同一份配置里。**一旦你手动选过一条直播源（直播历史 / 内置直播源 / 配置地址弹窗里填的），
这个开关会自动变成「关闭」**，之后换点播不会再改你选的直播源——除非你自己再打开它。

App 侧行为要记住两点：

- 清单是**权威来源**：在 App 里删掉一条内置源只删本地，下次刷新会按清单回来。
- 清单格式不对或里面没有可用条目时，刷新**只提示、不动**本地清单。

## 每次改完怎么推上去

先完成下方统一维护流程；下面只是普通清单提交示例。涉及自管直播时，须同时审阅并显式提交`live/selected.json`、相应M3U和必要文档/脚本，不能用`git add .`混入其他工作。

```bash
cd tv-source
# 用任意编辑器改 builtin.json
git add builtin.json
git commit -m "更新内置源清单"
git push github master    # 主仓库：App 实际拉取源，必须推
```

GitHub 的 HTTPS 推送走本机钥匙串令牌（`github.com` / 账号 `sukai616`），不会再问密码；

推完在浏览器打开加速前缀地址或直连 raw 地址，能看到新的 JSON 原文就算成功（能看到内容 = 仓库是公开的，App 才拉得到）。
**注意**：GitHub raw 也有几分钟的 CDN 缓存，推完立刻验证可能还是旧内容，等一下再试。

## 推送前自检（脚本）

`scripts/check_sources.py`，只用 Python 标准库，不用装依赖：

```bash
python3 scripts/check_sources.py                        # 只做静态检查：JSON 合法性、字段/URL 格式、地址重复、backup 规则
python3 scripts/check_sources.py --ipv6                 # 只做 IPv6 体检：本机到底有没有 IPv6 出口
python3 scripts/check_sources.py --sources              # 再看清单里每个地址抓不抓得到
python3 scripts/check_sources.py --live --workers 2  # 抓直播源 → 解析频道 → 抽测频道真的能不能播（自动带 IPv6 体检）
python3 scripts/check_sources.py --live --sample 20 --workers 2  # 旧：快速抽测（每源 20 条线路 / 20 个频道名）
python3 scripts/check_sources.py --live --full --phone --json-out /tmp/live-full.json --workers 2
                                                        # 新：贴近手机 + 全量（周维护用，可能跑很久）
python3 scripts/check_sources.py --live --git f2f4b5a --workers 2  # 顺手把某个提交里的旧清单也测一遍，做新旧对比
```

常用参数：

| 参数 | 含义 |
|------|------|
| `--sample N` | 每个源抽测 N 个（线路 / 频道名），默认 10；与 `--full` 并存时 **`--full` 优先** |
| `--full` | 全量：测该源全部可测线路，以及频道口径下全部频道名；公开直播默认且最多 `workers=2`，并默认开 `--deep`；每源完成打印进度，Ctrl+C 可中断（有 `--json-out` 会尽量落盘） |
| `--deep` | 更深「真能看」：响应若是 m3u8，解析第一条媒体分片或子播放列表并再请求；子列表再跟一层到分片；分片用 TS/fMP4/视频流特征判定，HTML/403/超时算挂。不加时行为与旧版兼容（拿到 m3u8 列表即过） |
| `--phone` / `--strict` | 贴近手机门槛预设：开 deep；`--min-pass` / `--min-pass-channel` 默认 **0.7**；**推荐源要求线路口径与频道口径都达标**（AND，不是 OR）；默认 `--max-lines 1`（只试该频道排序后的第一条，更贴近播放器常先试第一条） |
| `--channel-first-line` | 频道口径只试第一条线路（等价 `--max-lines 1`） |
| `--workers` | 并发数（公开直播默认且最多2；其他默认16、full默认4） |
| `--timeout` | 单请求超时秒数，默认 8（deep 跟进同样沿用） |
| `--min-pass` / `--min-pass-channel` | 线路 / 频道口径门槛（默认 0.5；`--phone` 下 0.7） |
| `--max-lines` | 频道口径每条频道最多试几条线路（默认 4；`--phone` 下 1） |
| `--force-ipv6` / `--vod` / `--json-out` | 强制测 IPv6、顺带测点播、完整结果落盘 |

判定「能播」的口径（默认）：HTTP 成功且响应像 m3u8 播放列表 / TS 切片 / 视频流
（看 `Content-Type` 和内容特征），HTML 错误页、403/404、超时、连不上都算挂。
加 `--deep`（或 `--full` / `--phone` 默认带上）后还会**跟进 m3u8 到分片**再判，更接近「手机点开真能看」。
**退出码 0 = 通过，1 = 有问题**（JSON 坏了、地址重复、推荐源没达标、一条都没通过），
适合推之前跑一遍或挂 CI；被跳过的源不计入失败。

公开直播的`--sample`仅作预筛，不能代替统一流程中的全量基础和逐台持续验收。全量可能跑很久（大源 2000+ 频道 × deep 跟分片）；日常推送用 `--sample`，清单大改或用户要求贴近手机时立刻跑 `--full --phone`（不必等周一）。

### 2026-11-06 测法审计：不再把「能下载」当「好用」

```bash
python3 scripts/check_sources.py --vod --vod-sample 8 --vod-playable --timeout 12
python3 scripts/check_sources.py --live --full --phone --timeout 8 --workers 2
python3 scripts/check_sources.py --live --sample 20 --phone --ffprobe --workers 2  # 有 ffprobe 时真读流
python3 scripts/test_check_sources.py                              # 误判回归夹具
```

- **点播结构**：完整响应、记录真实重定向、显式 gzip/deflate 解压；严格 JSON（兼容整行注释/尾逗号）、JS 变量/JSONP 外壳（只取 JSON，不执行）、`8位标记** + Base64`、JPEG/PNG/GIF/BMP 外壳及 App 同款 AES-CBC（调用本机 `openssl`）。空 `sites`、坏 JSON、只有 `spider` 字段、HTML、未知加密不再靠「出现 sites 字样」放行。多仓只报告，不自动算单仓可用。
- **点播质量**：主/站点级 spider（含 `./` 相对 URL）必须可下载且为可读 jar/ZIP、包含 `classes.dex`，声明了 MD5 就核对；均匀抽测 CMS JSON 或 type0 XML `列表→详情→首条播放地址`（XML不再因非JSON判死，拒绝DTD/ENTITY），分别报告列表成功和「媒体迹象」。jar 失效或 CMS 列表通过不足 50% 会报错。`--vod-playable` 的媒体失败单列，不能把本来有详情的站抹成「空列表」。
- **直播内容**：`--phone` 保持全量双口径 ≥70%，跟到分片（最多三层）；支持 M3U/TXT 的 UA/Referer/Origin/Cookie 后缀和 M3U 头（含 EXTHTTP/EXTVLCOPT，基础与持续检测共用解析），TS 要至少 3 个同步包、MP4/fMP4 看正确 box 偏移，**不能仅凭 `Content-Type: video/*` 或一个 0x47 通过**。频道口径复用同 URL 实测证据，避免第一轮通过、第二轮限流导致假 0%。
- **可选 ffprobe**：`--ffprobe` 对媒体 URL 再识别真实音/视频轨。这仍只证明取样时读到了流，不等于全天不卡、直播内容正确或所有分片都活着。

**仍有局限**：CSP jar 的格式可检不等于 App 内每个爬虫的搜索/播放可用；动态 Cookie、登录/授权码、防盗链私有算法、未知加密格式不绕过，需真机人工复核。抽样媒体、首分片及 ffprobe 不能测长期卡顿、持续追片、片源更新速度、VIP 解析成功率；单网络/单时段结果不能代表所有运营商，IPv6 无出口时只测域名线路。公开清单发现成人/会自动混入成人的源直接排除；仅名称关键词是提示，不替代人工看站构成。

### 公开直播统一维护流程：跨源逐台组合央视和地方台

目标是从不同订阅逐频道择优，形成一份覆盖央视与地方台的实测推荐表，不是只列少数无警告频道，也不是将某个大聚合整表当推荐。其他既有直播条目与URL保留，但排序、推荐标记与必要备注同样按真实持续证据更新；不能把“原样”理解为固定旧排名。仅适用于公开直播，点播与隐藏类别继续隔离。

1. **独占和复用**：核对Mac、两仓工作树、owner/PID及维护/媒体锁，保护用户改动；复用按完整URL＋头匹配的历史窗口，不并发重跑。设本轮/单源总预算，预算未测或断线不当源失效。
2. **目标矩阵**：央视1–17及5+为18基础台；先覆盖31省级卫视，再补常见地方/少儿。目标配置见live/channel-targets.json；HD/SD不重复计台，CCTV4欧洲/美洲、4K/8K及付费特色另列，不用CGTN/凤凰凑央视完整度。
3. **缺口驱动搜源**：用build_live_inventory.py从显式公开快照抽取所有目标台完整URL、头、别名和来源；先查现有和旧候选，再按缺台/错台/冻结/弱台扩大GitHub/Gitee、活跃维护者和论坛博客，不只换镜像；四个必查项目保留。
4. **去重与底层**：完整URL＋请求头精确去重，保留更稳替代，不因频道重合淘汰；记录真实重定向/CDN，多个IP或列表不等于独立运营者。完整query/必要UA/Referer保留，不公开Cookie/授权头、不伪造签名、不绕付费鉴权。
5. **基础与持续分开**：先低并发全量手机双70%基础验收；大规模分层准确列出未测，裸IPv6无出口跳过保留。再最多2并发逐台180–300秒，重点和优胜主备600秒，多轮对比，不与基础并跑。ENDLIST/冻结/旧片不充直播，FLV/直流用合适连续解码。
6. **身份与音画**：可见截帧实际看台标/节目，没看图标未核实；域名/名称/ffmpeg退出0不作身份成功。实际编码/分辨率/音轨单列，4K角标不等于4K，纯音频不计电视。保留损坏、EOF及节拍追赶原警告；追赶提示不直接等于坏帧或手机实卡。
7. **逐台选择主备**：优先身份正确、供给正常且解码健康的路线，结合画质/启动/同底层风险逐台组合。严格合格、带警告相对备选、仅基础/未长测分级，不把后三者混称完整流畅；不能因未达保守无警告门槛就只剩两台。日期签名URL需评估轮换和维护成本，不能把不同入口180/600秒混作同URL复验；不以假活凑完整。
8. **其他源也按实测排序**：按合格央视/省卫视/地方覆盖、持续证据广度与新鲜度、供给/损坏/画质、实际主备排序；保留条目和URL。少量样本只背书对应频道，不能用2台或HTTP汇总率推荐全表。证据不足明确待验证/相对推荐并合理靠后；同级缺证保持稳定顺序，不猜精确名次。保留2–3个有边界的相对推荐。
9. **最小发布**：只将经人工分级的公开台写selected.json，自管组合不自动整表导入。替换旧小名单为央地组合；升builtin版本，必要时同步App公开离线数组的排序/备注/推荐。回归和新增组合双70%通过后仅正常推GitHub，再核验固定raw/gh-proxy内容；不动隐藏、不打APK、保护UI/缓存。
10. **逐台完整交付**：央视18、省卫视31、地方补充与变体分表，逐台列完整主备URL/来源/头、基础与各独立持续窗口、身份/画质/音频/警告、相对/未测/缺台及维护风险。另列每个既有源排序、推荐与备注前后差异和依据。聊天明确各类真实覆盖、长测覆盖与不足，附完整文件，不能只说推荐几个。

每轮只读核实测量环境：代理配置是否存在与客户端是否实际采用分开，公开IP库查询使用相同HTTP客户端路径、只报大致地区/运营商，记录查询与媒体路由可不同及IP库误差；不能因Mac名字/时区称大陆网络。本次同urllib路径两库标美国洛杉矶，不是大陆运营商测试。未经授权不改网络/代理、不装VPN；弱网模拟不等于大陆出口。routine由父助手维护。

#### 可重复命令和指标边界

```bash
# 输入为本轮保存的公开*.playlist，以及[{"name":...,"url":...}]或文件路径→URL的来源映射
python3 scripts/build_live_inventory.py --snapshot-dir .audit-work/current/public-playlists --source-map .audit-work/current/public-sources.json --out-dir .audit-work/current/combined
python3 scripts/check_sources.py --live --full --phone --workers 2 --timeout 8 --json-out /tmp/live-basic.json
# 默认现在是18央视＋31省级卫视＋8补充逐台首选，并明确报告缺台；其他类别必须显式--channel
python3 scripts/check_live_stability.py --source '央卫精选' --seconds 180 --rounds 2 --json-out /tmp/cctv-quality.json
python3 scripts/check_live_stability.py --manifest /tmp/candidates.json --source '央视候选' --channel '^CCTV-?13$' --seconds 600 --decode-seconds 60 --decode-audio --json-out /tmp/cctv13-final.json
python3 -m unittest discover -s scripts -p 'test_*.py'
python3 scripts/refresh_curated_live.py --check
```

- `first_body_byte_seconds`是首个有效完整分片请求的首字节耗时（含DNS/TLS/响应头），`startup_complete_segment_seconds`是下载完第一片的时间，**两者都不是真实首帧**。
- 从直播边缘最后两片开始，以半target刷新最终重定向媒体playlist，保留其完整query，不能反复入口调度把不同后端序列拼作一条；旧跨后端跳序样本须按修正口径复验，不能直接判死。保存完整分片的序号、时长、耗时、字节数、哈希；重复playlist/重复payload不计新增，正常窗口重叠不误判回退。最高带宽变体不静默降画质，保存BANDWIDTH/RESOLUTION；每请求最多重试1次且保留首次错误。窗口结束不新起请求，已起请求保留正常超时，按实际墙钟计量。
- HLS低层`audit()`的`stable_sample`仅表示本次供给窗口：至少3不同片、供给比≥0.95、下载/媒体P95<0.7、无请求/验证失败或漏片、模拟不足≤1秒、最长无新片≤max(20秒,3×target)。不自动授予整表推荐。CLI默认补20秒可用视频/音频解码（不是180秒全程解码），`--decode-seconds 0`仅测供给并显式标范围，不能当整体合格；`--video-only-decode`显式省略音频。补解码时CLI另报`hls_supply_stable_sample`与`decode_clean_sample`，最终稳定标志需两者通过；`--decode-audio`保留为显式写法，仅请求可用第一音轨，不自动证明有音轨或音画同步。任何警告/损坏不可称无警告解码。`Resumed reading ... lag`是FFmpeg节拍读入追赶提示，严格标志仍为否，但不能仅据此推断损坏帧、手机实卡或网络根因；应与包损坏/解码错误分开报告。
- 连续工具共用`.live-quality.lock`并记录owner/PID，冲突即停、不自动抢锁；基础脚本尚不自行加该锁，外层独占维护者必须串行安排。JSON每台原子落盘；退出0只代表流程完成，不代表每台合格。解码阶段不混入HLS供给时长。
- 仅Mac当前网络，不能保证手机/晚高峰/异地，不把供给模拟说成播放器实际卡顿；未测音画同步/节目实时性，不归咎网络或播放器为已证实根因。加密/非HLS不算HLS稳定通过，不绕鉴权；另走授权范围内适当测法。

### 两个口径：线路 vs 频道

`--live` 会同时给两个口径，因为**多线路聚合源**（同一个频道名挂 2~6 条备用线路，
比如 `港澳台综合`、`备用1 完整版`）用单条线路口径会严重低估：

- **线路口径**：抽 `--sample` 个（或 `--full` 时全部）播放地址逐个探。只有一条线路的源看它就行。
- **频道口径**：抽 `--sample` 个（或 `--full` 时全部）**频道名**，每个最多试 `--max-lines` 条线路，**有一条能播就算这个频道可用**。
  只有平均线路数 ≥ 1.2 的源才真跑这一轮；单线路源两个口径等价，不会多花请求。
  `--phone` 默认 `max-lines=1`，只认排序后的第一条（更贴近播放器）。

**默认达标规则：两个口径有一个到门槛就算通过**（都不到才算挂）。
**`--phone` 下推荐源（以及报告里的 ✓/✗）要求两个口径都过**——更严，更贴近「列表里点开要稳」。
否则多线路聚合源用 OR 才能进推荐位。报告里多线路源会多打一行：

```
  ✓ 港澳台综合   频道 2334 · 抽测 20 · 可播  8 · 通过率  40% · 26.7s
        多线路源：604 个频道名平均 3.9 条线路；频道口径抽测 20 个，可用 15（75%）
```

同一条源 40%（线路）和 75%（频道）都对：前者说「单条线路的成活率」，后者说「用户点开这个台能不能看」。
**写清单 remark 时两个数都写上**，只写一个会误导。

### IPv6 体检

跑 `--live` 时会先体检一次：先看本机有没有全球 IPv6 地址（只有 `fe80::` 就是没配），
再真连一把双栈站点（解析 AAAA → TCP 连 443）——只有**能连出去**才算有 IPv6 出口，
IPv4 映射地址（`::ffff:1.2.3.4`）会被识破，不会误报。

没有 IPv6 出口时，**只剔除 IPv6 裸地址（`http://[2409:...]`）那些频道**，剩下的域名/IPv4 频道照测
（很多带「IPv6」名头的源里混着不少域名线路，整条跳过会把能播的也丢掉）；
只有整条源全是 IPv6 裸地址时才打 `⊘` 整条跳过——既不进通过名单，也不拉低结论。
想不加区分地全测一遍加 `--force-ipv6`。报告里的剔除/跳过是「本机测不了」，不代表源本身有问题。

## 清单格式

```json
{
  "version": 1,
  "vod": [
    { "name": "我的线路A", "url": "https://example.com/a.json", "remark": "自建", "recommended": true },
    { "name": "备用1", "url": "https://example.net/a.json", "remark": "同源备用域名", "backup": "我的线路A" }
  ],
  "live": [
    { "name": "我的直播", "url": "https://example.com/live.m3u", "remark": "" }
  ]
}
```

- `vod` 是点播配置（单仓 / 多仓 JSON 地址都行），`live` 是直播源（`txt` / `m3u` 地址）。
- 两个数组**可以只写一个**，另一个当作空。
- 每项 `url` **必填**（没地址的条目会被 App 跳过）；`name` 可留空（界面上退回显示地址）；`remark` 可选。
- `version` 目前 App 只当作普通字段忽略，留着方便以后做「清单有更新就提醒」。
- `recommended: true`（可选）标推荐位：App 的「内置源」列表里这些条目**排在最前面**，名字前多一段
  「推荐 · 」，备注跟在后面的括号里（例：`内置 · 推荐 · 饭太硬（主地址，Punycode 已验证）`）。
  没写就是普通条目。排序在 App 侧做，所以清单里不按推荐顺序写也不会乱。
- `backup: "主条目名"`（可选）标**同源备用**：这条必须是那个主地址的**同一份配置的另一个地址**
  （换个域名或路径），不是另一个资源。约定：
  - 备用不写 `recommended`（它是给主地址兜底的，不该自己占推荐位）；
  - 清单里放在**主条目的下一条**（App 会按“资源”分块排序，主条目是推荐位时备用跟着一起排到前面，
    两者永远挨在一起，不会被拆到列表两头）；
  - App 里显示成 `内置 · 备用 · 饭太硬 · 备用1（同源备用域名 fty.xxooo.cf）`。
  - **别把「同一个项目的另一个输出」当 `backup`**。比如 Guovin 的 `ipv4.m3u`（398 频道）和
    `result.m3u`（1180 频道）是两份不同的资源，只能各自当独立条目（跟 `小盒子` / `小盒子 4K` 一样）。
    误标成 `backup` 的后果：App 会把它当「同源副本」排到主条目旁边、显示成 `备用 ·`，但内容其实不一样，
    而且主条目一旦换掉它也跟着跑偏。`备用1 完整版` 就踩过这个坑，已改正。
- 地址里别带空格、换行、制表符：App 会清洗，但清洗过就和你在别处记的地址对不上了。
- 同一份清单里**不要重复**地址。

## 换源时的建议

- 只改必要的清单/自管白名单及验收脚本，保持 `builtin.json` 文件名/分支（App 里内置的那条地址是
  `https://gh-proxy.com/https://raw.githubusercontent.com/sukai616/tv-source/master/builtin.json`；换分支就同步改设置里的清单地址）。
- 仓库里的地址尽量用**免登录、无防盗链**的直链。网盘分享页（阿里云盘 / 夸克 / 百度网盘分享）App 直接 GET 拿不到。
- GitHub raw 国内不稳，用 `gh-proxy.com/`、`ghfast.top/` 这类加速前缀包一层（清单里已有例子）。
- 仓库被举报会封：重要的清单建议在对象存储（阿里云 OSS / 腾讯云 COS）再放一份，App 里换清单地址即可。

### 非HLS连续流与白名单周更

```bash
# HLS不支持FLV不是源失效；用FFmpeg视频连续解码，内部每轮有总时限
python3 scripts/check_continuous_stream.py --url '公开FLV完整URL' --name '频道名' \
  --seconds 180 --rounds 2 --json-out /tmp/flv-quality.json
# 通过后 --seconds 600 --rounds 1 复验。该工具共用.live-quality.lock，勿与HLS同时另开。
python3 scripts/refresh_curated_live.py --check  # selected.json和生成m3u是否一致
python3 scripts/test_curated_live.py
```

连续流记录FFmpeg视频解码进度、帧数、dup/drop、完整媒体时长/墙钟比、错误警告；不是HLS刷新供给，也不是首帧或手机卡顿率。不检查音画同步或节目画面真实性；`-re`节流自身会影响速度，不能把这些数字与HLS供给比当同一指标。已知冻结/ENDLIST不应改用解码通过来洗白。

维护顺序只以本文上方“公开直播统一维护流程：跨源逐台组合央视和地方台”为权威；本节仅说明非HLS及白名单工具，不能跳过逐台缺口、身份和长测矩阵。点播和隐藏专项维持各自隔离验收，不套央视完整度。

基础请求改为read1分块并检查读入总时限，避免无限滴流刷新socket超时；单源/全流程仍应另加外层总时限。预算终止为“未完成”，不是“源失效”。本周未改routine，由调度维护者采用上述流程。

`--decode-seconds`提供时额外报告`hls_supply_stable_sample`和`decode_clean_sample`，CLI的`stable_sample`要求两者均过；解码退出0但有损坏帧/警告绝不当无错误通过。低层`audit()`的稳定标志仍仅为HLS供给。

公开直播基础CLI默认且最多2 worker（显式更高值拒绝），与持续阶段串行；点播默认不变。覆盖元数据`target_coverage.strict/relative/basic_only`互斥，要求真实存在的逐台身份及对应时长证据，不能把仅基础通过计成长测合格。

持续HLS/连续流CLI支持`--network-label`，默认出口未核实；报告不得从Mac主机名/时区推定大陆。2026-11-16 16:01两家公开查询将本次urllib出口标为洛杉矶AS906，仅为查询路径观测；历史窗口/FFmpeg/媒体路由未逐一确认，不是大陆、手机或晚高峰保证。不得为模拟而自行改代理/VPN。
